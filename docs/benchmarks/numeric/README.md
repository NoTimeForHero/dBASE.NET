# Чтение числовых полей N и F

19 ноября 2026 года. База сравнения — `073cc251ed2cc6f6a3277fe0703f989381c1167e`. На обеих целях целые числа из ASCII до девяти цифр и поля из одних пробелов разбираются без строки. `N` возвращает `double`, `F` — `float`. На .NET Framework в остальных ASCII-полях пробелы по краям удаляются до декодирования, а число преобразуется тем же строковым методом. На .NET 8 используется встроенный `TryParse` из диапазона байтов. При пользовательской кодировке, байтах за пределами ASCII или неудачном прямом разборе сохраняется строковый путь. Изменения обошлись без новых зависимостей. [N](../../../dBASE.NET/Encoders/NumericEncoder.cs#L50), [F](../../../dBASE.NET/Encoders/FloatEncoder.cs#L23), [общий разбор байтов](../../../dBASE.NET/Encoders/FieldBytes.cs#L22)

## Условия и результаты

По каждой цели исходная и обновлённая библиотеки запущены последовательно с одинаковой версией стенда и той же парой DBF/FPT Harbour на 10 000 записей. SHA-256 входных файлов сверены с базовым отчётом. На `net472` использовался установленный .NET Framework 4.8.1, на `net8.0` — .NET 8.0.0. BenchmarkDotNet 0.15.8, Release, один запуск, три итерации прогрева и восемь измерительных с целью 200 мс. [Базовые условия](../efb9651/README.md), [сценарии стенда](../../../dBASE.NET.Tests/benchmarks/Harbour/HarbourReadBenchmarks.cs)

Для `PAY_AMOUNT` на Framework интервалы времени пересекаются, а аллокации уменьшились примерно на 35%. На .NET 8 BenchmarkDotNet отметил итерации короче 100 мс в двух сценариях чтения `ID` и `IS_PRINTED`. Фикстура производительности содержит числовые поля `N`. Тип `F` проверен на корректность, для него отдельного замера времени пока нет.
