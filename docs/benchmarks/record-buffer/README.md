# Чтение полей из буфера записи

19 ноября 2026 года. Сравниваются библиотека из `efb9651` и рабочая копия на базе `3b47f99036ce4f05638439fde20f11824a792c9d` с декодированием полей непосредственно из буфера строки и заранее заданной ёмкостью списка значений. Двоичные декодеры проверяют ширину своего поля. Указатель memo хранится отдельно, если его байты лежат в диапазоне общего массива. [Чтение записи](../../../dBASE.NET/DbfRecord.cs#L28), [указатель memo](../../../dBASE.NET/Encoders/MemoEncoder.cs#L58)

Оба варианта измерены на той же паре DBF/FPT Harbour с 10 000 строк. SHA-256 обоих файлов проверены по базовому отчёту. BenchmarkDotNet 0.15.8, Release, один запуск, три итерации прогрева и восемь измерительных итераций с целью 200 мс. Фактические рантаймы x64 — .NET Framework 4.8.1 для `net472` и .NET 8.0.0 для `net8.0`. [Базовые условия и команды](../efb9651/README.md)

Время указано как среднее ± `Error` BenchmarkDotNet в миллисекундах. Аллокации приведены в байтах на запись или на операцию открытия и закрытия.

Для полного прохода время сократилось на 6,3% под `net472` и на 15,1% под `net8.0`. Объём аллокаций уменьшился на 24,1% и 25,7% соответственно. У остальных сценариев интервалы времени до и после пересекаются. BenchmarkDotNet отметил короткую итерацию полного чтения на .NET 8 (85,1 мс при рекомендованных 100 мс), поэтому эффект по времени стоит повторно проверить, если от его величины зависит выбор следующей оптимизации.
