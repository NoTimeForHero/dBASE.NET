# Стоимость создания полных записей

На `7f5e1a0e030f61ed74ee943070ea9f4a48fbcf04` сравнили два существующих способа прочитать все поля, включая memo, в одном физическом порядке. База — `FastDbf.ReadRecords`, формирующий `DbfRecord` для каждой строки. `FastDbf.ReadValues` получает те же столбцы и создаёт `DbfRow` с массивом значений, переиспользуя контекст декодирования. Оба сценария суммируют `ID`, суммы сверяются с индексным чтением в подготовке. Все 109 обнаруженных тестов прошли, в том числе сверка обоих способов по всем значениям в фикстурах Harbour. [Стенд](../../../dBASE.NET.Tests/benchmarks/Harbour/HarbourReadBenchmarks.cs#L79) · [Сверка Harbour](../../../dBASE.NET.Tests/FastDBF/HarbourFixtures.cs#L18)

BenchmarkDotNet 0.15.8, Release, 10 000 строк исходной пары Harbour DBF/FPT, `net472` под .NET Framework 4.8.1 (4.8.9310.0), Windows x64. Один запуск, три итерации прогрева и восемь измерительных с целью 200 мс.

| Сценарий | Среднее ± `Error`, мс | Аллокации, байт/строку |
| --- | ---: | ---: |
| `ReadRecords` | 11,551 ± 0,500 | 1 012,18 |
| `ReadValues` для всех столбцов | 10,572 ± 0,230 | 651,19 |

Выборка всех столбцов сократила аллокации на 36% и время примерно на 8,5%. Это сравнение показывает суммарную стоимость представления строк и работы с контекстом. Упаковка значений входит в оба сценария, а замер даёт общее время без разбиения по CPU-стекам. Преобладающая стоимость создания объектов для условия о типизированном API не подтверждена.
