# Профиль последовательного чтения и эксперимент с типизированной проекцией

Замер от 19 ноября 2026 года. Код библиотеки соответствует `d6a0065`. BenchmarkDotNet 0.15.8, DLL `net8.0`, Release, SDK 10.0.404. Профиль выполнен на .NET 10.0.15 x64. Параметры прогрева и SHA-256 входных файлов Harbour совпадают с этапом `GetValue`. [Окружение](../get-value/README.md)

## Условие для переработки цикла

EventPipe снимал стеки в файловых `BlockReadValues`, `BlockReadAllValues` и `BlockReadRecords`. Отдельно проверили ту же узкую проекцию из предварительно загруженных DBF/FPT и синтетическую таблицу на 10 000 строк без memo. В широкой таблице 32 поля, восемь повторений `N(9)`, `L(1)`, `C(64)` и `D(8)`. Данные созданы вне измеряемого кода. Стенд сверяет контрольные суммы с индексным чтением. [Сценарии в памяти](../../../dBASE.NET.Tests/benchmarks/Harbour/MemoryReadBenchmarks.cs), [EventPipeProfiler](https://benchmarkdotnet.org/articles/features/event-pipe-profiler.html)

| Сценарий | Среднее, мс | Байт/строку | Тысяч строк/с |
| --- | ---: | ---: | ---: |
| `BlockReadValues` | 0,495 ± 0,017 | 94,60 | 20 187 |
| `BlockReadAllValues` | 3,665 ± 0,137 | 599,52 | 2 728 |
| `BlockReadRecords` | 4,040 ± 0,231 | 951,49 | 2 475 |
| `ScanHarbour` из памяти | 0,448 ± 0,019 | 94,59 | 22 302 |
| `ScanWide` из памяти | 7,133 ± 0,694 | 1 182,64 | 1 402 |

В стеке `DbfRecordReader.MoveNext` долю набирали главным образом дочерние операции чтения или копирования. Собственное время нарезки диапазонов `DbfReadColumn.Decode` в узком и широком сценариях из памяти составило 0,40% и 0,56%, а собственное время `DbfRecordReader.MoveNext` в узком сценарии — 0,06%. В широком сценарии заметны декодирование текста и дат. Профиль учитывает видимые управляемые стеки и может отнести инлайненный код к вызывающему методу. Свидетельств для отдельной переработки цикла на `ReadOnlySpan<byte>` недостаточно. ## Типизированная проекция

В двухстолбцовой проекции при заполненных значениях `object[2]` и две упакованные структуры занимают примерно 88 из 95 измеренных Б/строку. Это основание для узкого эксперимента. В изолированной сборке `net8.0` прежние декодеры предоставляют типизированные результаты `double?` и `bool?`, а перечисление отдаёт их в структуре вместе с физическим индексом и признаком удаления. Стенд сверил значения и метаданные каждой строки с обычной проекцией на обоих рантаймах. Новый публичный API потребовал бы определить контракт для остальных типов, столбцов и пустых значений. Эксперимент ограничен измерением потенциального эффекта на текущей паре полей.

SHA-256 исходной DLL — `6fbb0e606069132b7adcc639120cba4ee62e637cd1a7d35f7ccd0859fc13d765`, прототипа — `0ff379927ca9fd0156165cb7daF475fa70de9251fae9831ecc948e6b0f4c372d`. Процессы работали на .NET 10.0.15 и .NET 8.0.0. Контрольный объектный путь измерили в каждой DLL, поскольку выделение типизированных методов могло изменить код JIT и для вызовов через `IEncoder`.

| Рантайм | `ReadValues` исходный, мс | `ReadValues` в прототипе, мс | Типизированная выдача, мс | Байт/строку, до → типизированная | Тысяч строк/с, до → типизированная |
| --- | ---: | ---: | ---: | ---: | ---: |
| .NET 10 | 0,466 ± 0,039 | 0,515 ± 0,006 | 0,290 ± 0,004 | 94,60 → 6,60 | 21 468 → 34 471 |
| .NET 8 | 0,512 ± 0,083 | 0,867 ± 0,088 | 0,360 ± 0,006 | 94,60 → 6,60 | 19 543 → 27 810 |

На .NET 10 типизированный прототип на 38% уменьшил среднее время относительно исходной сборки, на обоих рантаймах аллокации уменьшились на 93%. Результат включает прямые вызовы двух конкретных декодеров и относится к этой схеме. Объектный путь внутри прототипа замедлился. Код прототипа оставлен в изолированном эксперименте. [Исходный JSON .NET 10](net10.0-typed-before.json), [эксперимент .NET 10](net10.0-typed-comparison.json), [исходный JSON .NET 8](net8.0-typed-before.json), [эксперимент .NET 8](net8.0-typed-comparison.json)

## Команды

```powershell
dotnet $benchDll $fixture --runtimes net10.0 --filter '*.BlockReadValues' '*.BlockReadAllValues' '*.BlockReadRecords' --profiler EP --launchCount 1 --warmupCount 3 --iterationCount 8 --iterationTime 200 --artifacts $artifacts
dotnet $benchDll $fixture --runtimes net10.0 --filter '*.ScanHarbour' '*.ScanWide' --profiler EP --launchCount 1 --warmupCount 3 --iterationCount 8 --iterationTime 200 --artifacts $artifacts
dotnet $benchDll $fixture --runtimes $target --filter '*.BlockReadValues' '*.TypedReadValues' --launchCount 1 --warmupCount 3 --iterationCount 8 --iterationTime 200 --artifacts $artifacts
```

Последняя команда относится к прототипу, для исходной DLL использовать только `*.BlockReadValues`.
