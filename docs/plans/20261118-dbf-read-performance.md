# План ускорения чтения DBF в dBASE.NET

Дата исследования — 18 ноября 2026 года.

План основан на статическом анализе рабочей копии форка на базе `0711bc7`. В ней уже есть изменения для открытия файлов только для чтения, подключения FPT по схеме и декодирования Harbour `@` и `=`. Базовый замер следует сделать на зафиксированной версии после сверки этих исправлений с Harbour. Приведённый порядок отражает ожидаемую пользу по коду. В рамках исследования замеры не проводились. [План совместимости с Harbour](20261118-harbour-fastdbf.md#2-эталон-чтения-в-harbour), [открытие FastDbf](../../dBASE.NET/FastDbf.cs#L33), [выбор декодеров](../../dBASE.NET/Encoders/EncoderFactory.cs)

## Порядок замеров на .NET Framework 4.7.2

Стенд Harbour на BenchmarkDotNet 0.15.8 покрывает открытие, последовательный `GetRecord`, чтение двух столбцов и чтение memo. Базовая серия на `efb9651` охватывает цели `net472` и `net8.0`. [Сценарии](../../dBASE.NET.Tests/benchmarks/Harbour/HarbourReadBenchmarks.cs), [базовые результаты](../benchmarks/efb9651/README.md)

1. **Подготовить входные данные и эталон.** Использовать 1 000 строк для проверки запуска и 10 000 строк для регулярных замеров. По мере добавления сценариев включать обычную и широкую схемы, DBF без memo и DBF с FPT. Для FPT включить пустые, короткие и многоблочные значения. DBT измерять отдельно при оптимизации его адаптера. На контрольных файлах сверить результаты `GetRecord`, `GetValue` и `IsDeleted` с Harbour, включая физический порядок записей, CP866, поля `@` и `=`, пустые значения и значимые пробелы в FPT. [Фикстуры и эталон](20261118-harbour-fastdbf.md)
2. **Зафиксировать базовый результат.** Собрать стенд в Release с целью `net472`. Записать фактическую версию .NET Framework, разрядность процесса, оборудование и размеры DBF/FPT. Для подтверждения работы именно на 4.7.2 нужен прогон на установленном рантайме 4.7.2. Цель `net472` сама по себе допускает запуск на более новом .NET Framework. В проекте библиотеки уже есть цель `net462`. [Цели проекта](../../dBASE.NET/dBASE.NET.csproj#L22), [версии .NET Framework](https://learn.microsoft.com/dotnet/framework/install/versions-and-dependencies)
3. **Раздельно измерить сценарии из таблицы ниже.** Использовать одни и те же входные файлы, поля, индексы и способ потребления результата. Сверять значения вне измеряемого участка. Сравнивать время, строки/с или запросы/с, выделенные байты на строку или запрос и количество сборок мусора. Для `Dbf.Read` полезно также измерять пиковую память. Прогреть JIT и отдельно фиксировать первое и повторное чтение файла. Первый проход в новом процессе может попасть в системный файловый кэш.
4. **После каждого этапа оптимизации повторять базовые сценарии.** Сначала проверить эквивалентность результатов, затем сравнить замеры с исходным и предыдущим вариантами. Это покажет вклад каждого этапа и возможную регрессию в точечном доступе.

| Сценарий | Базовый вариант и условия сравнения |
| --- | --- |
| Открытие | `FastDbf.ReadFile` до первого обращения к записи. Отдельно измерить DBF с FPT и без него. |
| Полный последовательный проход | Цикл `GetRecord` по физическим индексам. Сравнивать с пакетным чтением тех же полей и строк. `Dbf.Read` измерять отдельно как загрузку всей таблицы в память. |
| Последовательный проход по выбранным полям | `GetValue` для 1–3 столбцов на строку, особенно на широкой таблице. Пакетный вариант должен отдавать те же столбцы. Если сценарий фильтрует удалённые строки, включить `IsDeleted` в базовый замер. |
| Случайный доступ | `GetValue` и `GetRecord` на фиксированных последовательностях индексов. Проверить разреженную выборку и выборку с обращениями к соседним строкам. |
| Memo | На одном DBF/FPT измерить чтение выбранных полей без `M`, чтение части memo и чтение всех memo. Отдельно учитывать стоимость открытия и, для `Dbf.Read`, копирования FPT/DBT. |
| Декодирование в памяти | Декодировать заранее загруженные байты. Сравнить размещение полей в буфере и варианты декодеров независимо от файлового ввода-вывода. |

## Порядок оптимизаций на .NET Framework 4.7.2

1. **Декодировать поля из общего буфера записи. Выполнено.** `DbfRecord` передаёт диапазоны массива декодерам и задаёт ёмкость списка по числу полей. Байты указателя memo сохраняются для записи. [Сравнение с базой](../benchmarks/record-buffer/README.md), [DbfRecord](../../dBASE.NET/DbfRecord.cs#L28), [MemoEncoder](../../dBASE.NET/Encoders/MemoEncoder.cs#L58)
2. **Читать последовательные записи блоками и декодировать выбранные столбцы. Выполнено.** `FastDbf.ReadRecords`, `FastDbf.ReadValues` и `Dbf.Read` используют общий блоковый читатель. Каждое перечисление подготавливает смещения и декодеры один раз, читает блоки до 64 КиБ по 64-битным файловым смещениям и обрабатывает метку `0x1A` на границе записи. Проверены короткие чтения, неполная последняя запись и владение байтами указателя memo. [Сравнение с индексным чтением](../benchmarks/block-read/README.md), [FastDbf](../../dBASE.NET/FastDbf.cs#L125), [блоковый читатель](../../dBASE.NET/DbfRecordReader.cs)
3. **Убрать промежуточные строки в декодерах.** Типовые `L` и `D` уже разбираются напрямую из байтов. Далее для `N` и `F` проверить `Utf8Parser` на ASCII-значениях с проверкой полного потребления поля. Для остальных представлений использовать строковый декодер. Сверить пустые поля, знак, экспоненту, округление и ошибки разбора. Для `C` проверить декодирование только полезного диапазона байтов, сохранив правила `Trim()` и пользовательских кодировок. Для бинарных полей сравнить `Unsafe.ReadUnaligned<T>` с `BitConverter` по смещению или `BinaryPrimitives` после проверки границ и с учётом порядка байтов. `System.Memory` с `ReadOnlySpan<byte>` и `Utf8Parser`, а также пакет `Unsafe` доступны для `net462`. [Замеры L и D](../benchmarks/logical-date/README.md), [числа](../../dBASE.NET/Encoders/NumericEncoder.cs#L50), [текст](../../dBASE.NET/Encoders/CharacterEncoder.cs#L43), [System.Memory](https://www.nuget.org/packages/System.Memory/4.6.3), [Unsafe](https://www.nuget.org/packages/System.Runtime.CompilerServices.Unsafe/6.1.2)
4. **Оптимизировать memo по отдельному профилю.** На проходе по выбранным столбцам читать содержимое только запрошенных memo. Для FPT убрать выделение и реверс массива под четырёхбайтовую длину, переиспользовать буфер содержимого и сохранить пробелы. Для DBT читать блоки за один проход с поиском пары `0x1A 0x1A`, включая случай на стыке блоков. Копирование всего memo в `Dbf.Read` обеспечивает редактирование после чтения. Для отдельного режима только чтения оценить доступ к исходному FPT/DBT по мере обращения. Если memo доминирует в базовом профиле, проверить этот этап сразу после блочного чтения. [Копирование memo](../../dBASE.NET/Dbf.cs#L115), [FPT](../../dBASE.NET/Memo/Adapters/FoxProAdapter.cs), [побайтовый поиск в DBT](../../dBASE.NET/Memo/Adapters/Dbase3Adapter.cs#L69)
5. **Сравнить `MemoryMappedFile` для частого случайного доступа.** Проверять на неизменяемом файле с теми же индексами, что и у буферизованного чтения, включая стоимость создания отображения. Для разреженных выборок также проверить точечный доступ с переиспользуемым буфером. Открытие `FastDbf` с `readOnly: true` допускает запись другим процессом через `FileShare.ReadWrite`. При совместном доступе выбор буферизации зависит от требуемой видимости внешних изменений. [Открытие файла](../../dBASE.NET/FastDbf.cs#L33), [MemoryMappedFile](https://learn.microsoft.com/en-us/dotnet/api/system.io.memorymappedfiles.memorymappedfile?view=netframework-4.8.1)

Если после этих этапов в профиле преобладает создание объектов, измерить потоковую выдачу выбранных значений через типизированный API. Полный `DbfRecord` хранит `List<object>`, поэтому значения примитивных типов упаковываются при добавлении. Типизированный путь может убрать упаковку и создание объектов записей в сценариях импорта и агрегации. [Хранение записи](../../dBASE.NET/DbfRecord.cs#L54)

## Цели сборки и NuGet-пакет

- Один пакет dBASE.NET содержит отдельную DLL в `lib/<TFM>/` для каждой из целей `net462;net48;netstandard2.0;net8.0`. Для приложений на .NET Framework 4.7.2 есть сборка `net462`. Первый быстрый путь в `net8.0` заполняет блок через `Stream.ReadAtLeast` со `Span<byte>`. NuGet выбирает подходящую DLL по TFM проекта-потребителя. Сохранять совместимый публичный API у всех сборок. [Цели проекта](../../dBASE.NET/dBASE.NET.csproj#L22), [Несколько TFM в одном NuGet-пакете](https://learn.microsoft.com/en-us/nuget/create-packages/supporting-multiple-target-frameworks), [Правила совместимости NuGet](https://learn.microsoft.com/en-us/dotnet/standard/library-guidance/nuget-package-compatibility-rules)
- Добавлять `net10.0` и `net11.0` по мере появления быстрых путей, которым нужны API этих версий. Структура записи, проверка границ и семантика разбора DBF остаются общими для всех целей. Использовать условную компиляцию точечно, внутри операций чтения и декодирования. Если для операции потребуется несколько реализаций, проверять ветки от новой к старой в порядке `#if NET11_0_OR_GREATER`, `#elif NET10_0_OR_GREATER`, `#elif NET8_0_OR_GREATER`, затем общий вариант через `#else`. [Символы условной компиляции C#](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/preprocessor-directives)
- В отчётах указывать TFM сборки и фактический рантайм процесса. Условная компиляция выбирает код по TFM при сборке. JIT и реализации уже используемых API зависят от фактического рантайма, поэтому DLL для `net8.0` может получить ускорение при запуске на .NET 10 или .NET 11. [Выбор рантайма .NET](https://learn.microsoft.com/en-us/dotnet/core/versions/selection), [Изменения производительности в .NET 11](https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-11/)

## Замеры на .NET 8, 10 и 11

1. Собрать DLL `net8.0` один раз, записать её SHA-256 и использовать этот же бинарный файл на .NET 8, 10 и 11. Проверять версию рантайма в процессе, который выполняет замер. Использовать те же 10 000 строк DBF/FPT, кодировку, параметры прогрева и способы потребления результата. Сохранить время, строки/с и байты аллокаций на запись. Если добавится быстрый путь на новом API, сравнить его с той же DLL `net8.0` на одном рантайме. [Базовые условия замера](../benchmarks/efb9651/README.md)
2. На .NET 11 проверить циклы по `ReadOnlySpan<byte>` с фиксированным шагом. Сравнить обработку заранее загруженного блока при известном при компиляции шаге и при длине записи из DBF-заголовка, постоянной на протяжении прохода. По дизассемблированному коду проверить, какие проверки границ убрал JIT, и измерить влияние на полный проход по таблице. [Оптимизации циклов в .NET 11](https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-11/)
3. На Windows проверить синхронный `RandomAccess.Read` на дескрипторе, открытом с `FileOptions.Asynchronous`. Сравнить .NET 10 и .NET 11 на одних смещениях и размерах чтения и отдельно измерить дескриптор без этого флага. Сначала замерить время и аллокации самого чтения, затем проверить эффект в сценарии чтения DBF. [Оптимизация RandomAccess.Read в .NET 11](https://devblogs.microsoft.com/dotnet/performance-improvements-in-net-11/)
