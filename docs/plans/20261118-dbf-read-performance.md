## Порядок замеров на .NET Framework 4.7.2

Стенд Harbour на BenchmarkDotNet 0.15.8 покрывает открытие, последовательный `GetRecord`, чтение двух столбцов и чтение memo. Базовая серия на `efb9651` охватывает цели `net472` и `net8.0`. [Сценарии](../../dBASE.NET.Tests/benchmarks/Harbour/HarbourReadBenchmarks.cs), [базовые результаты](../benchmarks/efb9651/README.md)

1. **Подготовить входные данные и эталон.** Использовать 1 000 строк для проверки запуска и 10 000 строк для регулярных замеров. По мере добавления сценариев включать обычную и широкую схемы, DBF без memo и DBF с FPT. Для FPT включить пустые, короткие и многоблочные значения. DBT измерять отдельно при оптимизации его адаптера. На контрольных файлах сверить результаты `GetRecord`, `GetValue` и `IsDeleted` с Harbour, включая физический порядок записей, CP866, поля `@` и `=`, пустые значения и значимые пробелы в FPT. [Фикстуры и эталон](20261118-harbour-fastdbf.md)
2. **Зафиксировать базовый результат.** Собрать стенд в Release с целью `net472`. Записать фактическую версию .NET Framework, разрядность процесса, оборудование и размеры DBF/FPT. Для подтверждения работы именно на 4.7.2 нужен прогон на установленном рантайме 4.7.2. Цель `net472` сама по себе допускает запуск на более новом .NET Framework. В проекте библиотеки уже есть цель `net462`. [Цели проекта](../../dBASE.NET/dBASE.NET.csproj#L22), [версии .NET Framework](https://learn.microsoft.com/dotnet/framework/install/versions-and-dependencies)
3. **Раздельно измерить сценарии из таблицы ниже.** Использовать одни и те же входные файлы, поля, индексы и способ потребления результата. Сверять значения вне измеряемого участка. Сравнивать время, строки/с или запросы/с, выделенные байты на строку или запрос и количество сборок мусора. Для `Dbf.Read` полезно также измерять пиковую память. Прогреть JIT и отдельно фиксировать первое и повторное чтение файла. Первый проход в новом процессе может попасть в системный файловый кэш.
4. **После каждого этапа оптимизации повторять базовые сценарии.** Сначала проверить эквивалентность результатов, затем сравнить замеры с исходным и предыдущим вариантами. Это покажет вклад каждого этапа и возможную регрессию в точечном доступе.

| Сценарий | Базовый вариант и условия сравнения |
| --- | --- |
| Открытие | `FastDbf.ReadFile` до первого обращения к записи. Отдельно измерить DBF с FPT и без него. |
| Полный последовательный проход | Цикл `GetRecord` по физическим индексам. Сравнивать с пакетным чтением тех же полей и строк. `Dbf.Read` измерять отдельно как загрузку всей таблицы в память. |
| Последовательный проход по выбранным полям | `GetValue` для 1–3 столбцов на строку, особенно на широкой таблице. Пакетный вариант должен отдавать те же столбцы. Если сценарий фильтрует удалённые строки, включить `IsDeleted` в базовый замер. |
| Случайный доступ | `GetValue` и `GetRecord` на фиксированных последовательностях индексов. Проверить разреженную выборку и выборку с обращениями к соседним строкам. |
| Memo | На одном DBF/FPT измерить чтение выбранных полей без `M`, чтение части memo и чтение всех memo. Отдельно учитывать стоимость открытия и, для `Dbf.Read`, копирования FPT/DBT. |
| Декодирование в памяти | Декодировать заранее загруженные байты. Сравнить размещение полей в буфере и варианты декодеров независимо от файлового ввода-вывода. |

## Порядок оптимизаций на .NET Framework 4.7.2

1. **Декодировать поля из общего буфера записи. Выполнено.** `DbfRecord` передаёт диапазоны массива декодерам и задаёт ёмкость списка по числу полей. Байты указателя memo сохраняются для записи. [Сравнение с базой](../benchmarks/record-buffer/README.md), [DbfRecord](../../dBASE.NET/DbfRecord.cs#L28), [MemoEncoder](../../dBASE.NET/Encoders/MemoEncoder.cs#L58)
2. **Читать последовательные записи блоками и декодировать выбранные столбцы. Выполнено.** `FastDbf.ReadRecords`, `FastDbf.ReadValues` и `Dbf.Read` используют общий блоковый читатель. Каждое перечисление подготавливает смещения и декодеры один раз, читает блоки до 64 КиБ по 64-битным файловым смещениям и обрабатывает метку `0x1A` на границе записи. Проверены короткие чтения, неполная последняя запись и владение байтами указателя memo. [Сравнение с индексным чтением](../benchmarks/block-read/README.md), [FastDbf](../../dBASE.NET/FastDbf.cs#L125), [блоковый читатель](../../dBASE.NET/DbfRecordReader.cs)
3. **Убрать промежуточные строки в декодерах. Выполнено.** Типовые `L` и `D` уже разбираются напрямую из байтов. Для `N` и `F` готов прямой разбор коротких ASCII-целых. На Framework дроби и другие форматы сохраняют штатное преобразование с округлением этого рантайма, а на .NET 8 добавлен разбор чисел из диапазона байтов. Для `C` обычные пробелы в системных кодировках с подходящим обработчиком неверных байтов убираются до декодирования. Для бинарных полей сохранён `BitConverter` по смещению. `Unsafe.ReadUnaligned<T>` и `BinaryPrimitives` быстрее в микробенчмарке, абсолютная экономия на 20 000 чтений примитивов составила до 45 мкс. [Замеры L и D](../benchmarks/logical-date/README.md), [числовой разбор](../benchmarks/numeric/README.md), [замеры C](../benchmarks/character/README.md), [бинарные поля](../benchmarks/binary-fields/README.md)
4. **Оптимизировать memo по отдельному профилю. Выполнено.** При выборке столбцов читается содержимое только запрошенных memo. FPT читает длину без временного массива, переиспользует буфер и сохраняет принятую семантику пробелов. DBT находит пару `0x1A 0x1A` за один блочный проход, включая стык двух чтений. `FastDbf` в режиме только чтения уже обращается к исходному sidecar по мере необходимости. Копия memo в `Dbf.Read` обеспечивает редактирование. [Замеры memo](../benchmarks/memo/README.md), [копирование memo](../../dBASE.NET/Dbf.cs#L115), [FPT](../../dBASE.NET/Memo/Adapters/FoxProAdapter.cs), [DBT](../../dBASE.NET/Memo/Adapters/Dbase3Adapter.cs)
5. **Сравнить `MemoryMappedFile` для частого случайного доступа. Выполнено.** На неизменяемой DBF при одинаковых индексах отображение быстрее буферизованного потока в 1,42× на 128 запросах и в 20,69× на 10 000. Учитывались открытие файла и создание отображения. Результат относится к чтению восьми байтов поля с прогретым файловым кэшем. В `FastDbf` сохранён `FileStream` с `FileShare.ReadWrite` для совместного доступа. [Замеры случайного доступа](../benchmarks/random-access/README.md), [открытие файла](../../dBASE.NET/FastDbf.cs#L33)

Если после этих этапов в профиле преобладает создание объектов, измерить потоковую выдачу выбранных значений через типизированный API. Контрольное сравнение было выполнено с одинаковым набором столбцов. Переход с `ReadRecords` на `ReadValues` уменьшил аллокации на 36% и время на 8,5%. Оба пути по-прежнему упаковывают значения. Полученный замер не подтвердил условие для отдельного эксперимента с типизированным API. [Контрольный замер](../benchmarks/record-materialization/README.md), [хранение записи](../../dBASE.NET/DbfRecord.cs#L54)

## Цели сборки и NuGet-пакет

Добавить `net10.0` в пакет, когда отдельному быстрому пути потребуется API этой версии и замеры подтвердят его пользу. Сохранить совместимый публичный API и общие правила разбора DBF. Снять исходный результат и результат оптимизации в одной серии на .NET 10. Для исходного варианта взять родительский коммит первого изменения, а для сверки истории использовать сохранённые замеры. Записывать TFM стенда, TFM и SHA-256 DLL, SDK и фактическую версию рантайма процесса замера. Если появится отдельная реализация `net10.0`, показать её результат отдельной строкой на том же .NET 10. [Выбор рантайма .NET](https://learn.microsoft.com/en-us/dotnet/core/versions/selection)
4. **Сохранить результаты этапа в `docs/benchmarks/<этап>/`.** Положить `README.md` со сценариями, командами, SHA коммитов, параметрами и хешами фикстур, окружением, средним временем и разбросом, строками или запросами в секунду, выделенными байтами на строку или запрос и замеченными регрессиями. Рядом сохранить JSON BenchmarkDotNet до и после с названием рантайма в имени файла. При ускорении только микросценария явно зафиксировать результат полного чтения, даже если разница укладывается в шум. [Пример отчёта](../benchmarks/numeric/README.md)
