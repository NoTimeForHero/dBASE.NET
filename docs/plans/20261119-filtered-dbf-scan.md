# Потоковая фильтрация и типизированное чтение DBF

Статус: выполнен

Дата: 19 ноября 2026 года. Исходный коммит `23ef13b3a22354b01438b318577c22506ab5bf60`, ветка `beta`.

## Контекст

`FastDbf.ReadValues` уже читает файл блоками до 64 КиБ и готовит смещения столбцов один раз за проход. Однако каждый вызов перечислителя формирует `object[]` и декодирует всю указанную проекцию, прежде чем вызывающий код сможет проверить признак удаления или фильтр. Числа `N` возвращаются в виде упакованных `double`. Отдельный прототип двух типизированных полей на .NET 10 x64 сократил время с 0,466 до 0,290 мс и аллокации с 94,60 до 6,60 Б/строку на другой фикстуре. [Блочное чтение](../../dBASE.NET/DbfRecordReader.cs) · [Эксперимент с типизированной проекцией](../benchmarks/sequential-profile/README.md)

На синтетическом наборе Keystone `requests.dbf` занимает около 200 МиБ, содержит 65 656 физических записей по 3 194 байта. Фильтр `CITY = 78 AND STATUS = 'A'` даёт 32 видимых совпадения. Текущий путь сначала декодирует все три поля `CITY`, `STATUS` и `TICKET`. Медианы двух серий на .NET Framework 4.8.1 x86 — 65,99 и 65,85 мс, на .NET 10.0.15 x86 — 49,52 и 54,57 мс. Справочник из 50 000 улиц (`ID N`, `CITY N`, `NAME C`, CP866) загружается в словарь за 15,78 и 17,96 мс соответственно. Городской справочник к этому этапу не относится.

## Публичный контракт

1. Добавить синхронный `FastDbf.VisitRows(DbfRowVisitor visitor, params int[] columns)`. Перечислять записи в физическом порядке, включая помеченные удалёнными. Колонки указываются нулевыми индексами схемы, их порядок определяет нулевые позиции в представлении строки. Пустая проекция позволяет проверить метаданные. Повторы допустимы. Аргументы и выбранные столбцы проверяются до обхода.
2. `DbfRowReader` — `readonly ref struct`, доступный во время вызова обработчика. Он возвращает нулевой физический индекс и признак удаления. `GetNumber` возвращает `double?` для `N`, `GetText` возвращает `string` для `C`, `GetValue` использует существующий объектный декодер. Значения декодируются при обращении и могут жить дольше обработчика. На каждую строку обход не выделяет `object[]`. Прерывание обработчика исключением прекращает текущий вызов. Повторный `VisitRows` начинает проход с первой записи. [Ограничения `ref struct`](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/builtin-types/ref-struct)
3. Пустые числа, числовые форматы, текстовые пробелы, CP866 и пользовательские кодировки должны иметь ту же семантику, что у соответствующего декодера `ReadValues`. Вызов типизированного метода для другого типа поля завершается `InvalidOperationException`. Блочный буфер принадлежит библиотеке, обработчик обязан соблюдать текущий контракт `FastDbf` и держать таблицу открытой, пока идёт обход. Существующие `ReadValues`, `ReadRecords`, точечное чтение и запись продолжают использовать свои публичные контракты.

## Реализация и измерения

1. Переиспользовать `DbfRecordReader`, подготовку `DbfReadColumn` и `EncoderContext`. В типизированном числовом пути использовать существующий разбор коротких ASCII-целых без упаковки, для других чисел вызывать стандартный `NumericEncoder.Decode`. Для текста использовать `CharacterEncoder.Decode`. Подготовка колонки должна выбирать тот же декодер по схеме. Отдельная оптимизация односимвольного поля возможна после замера, если на нём остаётся заметная доля времени.
2. В поисковом стенде проверить флаг удаления в начале обработчика, затем получить `CITY`, получить `STATUS` только для нужного города и `TICKET` только для совпавших строк. Возвращать тот же упорядоченный список `(RecNo, TICKET)` с `RecNo` от 1. Для улиц строить свежий `Dictionary<int, (int CityId, string Name)>`, включая открытие, декодирование CP866, обрезку правых пробелов и закрытие файла в обоих вариантах.
3. Сравнить `ReadValues` и `VisitRows` в одном процессе подготовки BenchmarkDotNet на каждой платформе. Для поиска отдельно измерить проход только по метаданным, чтобы оценить стоимость блочного чтения и обхода. Вывести медианы, разброс и аллокации. Сверить всю последовательность поиска и содержимое словаря вне замеров, включая повторный запуск. Использовать один и тот же малый набор около 1 МиБ для проверки и один набор 200 МиБ для замеров. На время чтения использовать синтетические данные, `readOnly: true` и консольный процесс. Записать версии рантаймов, разрядность, методику и хеши файлов. Изменение размера блока, SIMD и индексы оставить для отдельных измерений.

## Критерии готовности

- Сборка библиотеки для `net462`, `net48`, `netstandard2.0` и `net8.0`. Проверка на установленном .NET Framework 4.8.1 и .NET 10 x86.
- Регрессии для порядка проекции и дубликатов, физического индекса, удаления, перехода между блоками, CP866, пустых значений, ошибочных аргументов и типа поля. Сравнить объектный доступ через новый API с `ReadValues`. Проверить, что необращение к полю действительно пропускает его декодирование. Прогнать существующие тесты Harbour и memo.
- Убедиться в совпадении SHA-256 тестовых DBF/FPT и в эквивалентности всех результатов. Записать наблюдаемую разницу на обоих рантаймах и отдельно оценить стабильность объектного пути. Если выигрыш ограничивается конкретным сценарием, указать это в результатах.

## Запуск стенда

Нужны синтетические файлы Keystone `requests.dbf`, `requests.fpt` и `streets.dbf` в одном каталоге. Команды выполняются из корня dBASE.NET с .NET SDK 10 и targeting pack .NET Framework 4.7.2. Для .NET 10 x86 указать `dotnet.exe` из отдельного SDK x86. Библиотека для стенда `net472` собирается под `net462`, для стенда .NET 10 — под `net8.0`. [Сценарии](../../dBASE.NET.Tests/benchmarks/Harbour/KeystoneScanBenchmarks.cs)

```powershell
$project = 'dBASE.NET.Tests/benchmarks/Harbour/HarbourBenchmarks.csproj'
$out = Join-Path $PWD 'BenchmarkDotNet.Artifacts/keystone-scan'
$small = 'D:\path\to\dbf-benchmark-1mib\requests.dbf'
$full = 'D:\path\to\dbf-benchmark-200mib\requests.dbf'
$dotnetX86 = 'D:\path\to\dotnet-10-x86\dotnet.exe'
$env:DbaseIncludeNet10 = 'true'
$options = @('--filter', '*', '--platform', 'X86', '--launchCount', '2', '--warmupCount', '3',
             '--iterationCount', '8', '--iterationTime', '200', '--outliers', 'DontRemove')

dotnet build $project -c Release -f net472 -p:PlatformTarget=x86 -o "$out/host-net472"
& "$out/host-net472/HarbourBenchmarks.exe" $small --keystone --verify
& "$out/host-net472/HarbourBenchmarks.exe" $full --keystone --verify
& "$out/host-net472/HarbourBenchmarks.exe" $full --keystone @options --artifacts "$out/net472"

& $dotnetX86 build $project -c Release -f net10.0 -p:PlatformTarget=x86 -o "$out/host-net10.0"
& $dotnetX86 "$out/host-net10.0/HarbourBenchmarks.dll" $small --keystone --verify
& $dotnetX86 "$out/host-net10.0/HarbourBenchmarks.dll" $full --keystone --verify
& $dotnetX86 "$out/host-net10.0/HarbourBenchmarks.dll" $full --keystone @options --cli $dotnetX86 --artifacts "$out/net10.0"
```

## Результаты

Стенд подтвердил одну пару на малом наборе и 32 пары на полном. Проверены порядок, повторный проход и все 50 000 записей словаря улиц на обоих рантаймах. Файлы открывались только для чтения, CDX были недоступны в ходе замеров. SHA-256 всех файлов совпали до и после. Собраны четыре целевые платформы библиотеки. На .NET Framework прошли 110 тестов, включая наборы Harbour и memo. На .NET 10 x86 прошла отдельная проверка стенда Harbour.

BenchmarkDotNet 0.15.8, Release, Windows 10, Intel Core i7-12700K, x86, прогретый файловый кэш. Два процесса по восемь измерительных итераций на метод. В таблице медиана и квартильный диапазон [Q1–Q3], затем управляемые аллокации на операцию. Файл открыт до замера поиска. Для улиц оба варианта открывают и закрывают файл внутри замера. Сырые отчёты и хеши финальной серии в `BenchmarkDotNet.Artifacts/20261119-keystone-scan/final-run/`.

Проход только по метаданным занял 38,114 мс на Framework и 31,988 мс на .NET 10. Текущее время фильтра близко к этому контрольному проходу. Замер включает обход строк и чтение всей широкой таблицы из файлового кэша.

Первый вариант общего числового декодера с упаковкой `double?` замедлил объектный путь в контрольном прогоне Framework. Финальный вариант использует прямой типизированный разбор ASCII-целых и обращается к существующему числовому декодеру для остальных форматов. В дополнительном контроле одну и ту же программу запускали последовательно с оригинальной, дважды с изменённой и снова с оригинальной DLL. На процесс пришлось шесть прогревов и 16 итераций. Диапазоны медиан `ReadValues` до и после пересеклись на обоих рантаймах и в обоих сценариях. Хеши DLL и значения сохранены в `final-run/object-control-*.txt`.
